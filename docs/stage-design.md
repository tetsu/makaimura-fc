## 2. スコア・エクステンド（1UP）・HUD 規約

### 2.1 スコア加算表（100点単位で管理、HUD 6桁表示 `000000`）

| イベント | 加算点 | 内部加算値 (`ap_add_score` 引数) |
| --- | ---: | ---: |
| ゾンビ撃破 | 100 | `1` |
| 固定敵・ツボ持ち敵・固定砲台撃破 | 200 | `2` |
| 武器・鎧アイテム取得 | 100 | `1` |
| ボス鍵取得 | 500 | `5` |
| ボス撃破 | 1,000 | `10` |

### 2.2 エクステンド（1UP）規約
- 新規ゲーム開始時（タイトルから Right+START）：スコア `000000`、残機 `3`、次回エクステンド目標を **2,000点**（内部値 `20`）に設定。
- スコアが目標に達すると残機を `+1`（上限 `9`）、SE（`snd_se_key`）を再生し、次回目標を **+5,000点**（内部値 `+50`、すなわち 2,000 → 7,000 → 12,000 ...）に更新する。
- ミス復帰・ステージ移行時はスコアとエクステンド目標を引き継ぐ。タイトル復帰またはゲームオーバー後の新規開始時にリセットする。
- 全7区間完成時（Task 4-3/4-4）にアーケード準拠の 20,000 / 70,000 点へ調整可能な定数設計とする。

### 2.3 アーケードモード HUD レイアウト（固定上端4行）
- Row 1 (`$2023`): `STG # LIFE # TIME ### CP # W`（`W` = 武器 `L`/`D`/`T`/`S`）
- Row 2 (`$2043`): `SCORE ######    LP #`（スコア6桁・下2桁 `00` 固定、右側に周回数 `LP 1` / `LP 2`）

## 3. `$8000` ステージバンク共通バイナリ仕様

各ステージバンク（`BANK12+`）は既存 `stage_header`（`$8001..$8012`）とパレット表を維持したまま、固定アドレス **`$8080`** にアーケードステージ記述子（`arcade_stage_desc`）を配置する。`BANK3`（`$A000`）はこの固定オフセットを直接参照することで、ステージ番号のハードコード分岐なしに全ステージを駆動する。

### 3.1 縦複数ページマップ配置規約
- `map_col_stride = 16`（1列16メタタイル = 256 px）を維持する。
- 縦2ページステージ（`stage_width_cols = 16`, `stage_height_rows = 30` = 480 px）では、`read_map_cell` が `row >= 16` のときに自動で `col += stage_width_cols`, `row -= 16` へ変換する。
  - 縦ページ 0（`row 0..15`, world Y `0..255`）: マップ先頭 16 列（256 B）
  - 縦ページ 1（`row 16..29`, world Y `256..479`）: マップ後半 16 列（256 B）

### 3.3 JSON からステージデータを生成する

`tools/convert-stage-map.py` は、手元で作成した地形、初期配置、敵の出現設定を ca65 のインクルードに変換する。

```powershell
python tools/convert-stage-map.py stage.json build/stage.inc --prefix test_stage
```

```json
{
  "tiles": [
    ["sky", "sky", "sky", "sky", "sky", "sky", "sky", "sky",
     "sky", "sky", "sky", "sky", "sky", "sky", "sky", "sky"],
    ["rock", "rock", "rock", "rock", "rock", "rock", "rock", "rock",
     "rock", "rock", "rock", "rock", "rock", "rock", "rock", "rock"]
  ],
  "palette_pairs": [0, 0, 1, 1, 2, 2, 3, 3],
  "items": [{"type": "armor", "x": 80, "y": 16}],
  "platforms": [{"type": "horizontal", "x": 112, "y": 8, "span": 32}],
  "enemies": {
    "fixed": {"x": 160, "y": 16},
    "pot": {"x": 208, "y": 16, "drop": "dagger"}
  }
}
```

- `tiles` は画面上から下へ並べた行で、幅は16・32・48列、高さは1〜32行。セルには `sky`、`gravel`、`ledge`、`rock`、`oneway`、`ladder`、`hazard` を指定する。実行時に既存のメタタイル表が描画と衝突属性を決める。各ページを列優先で出力し、最後のページの不足分は岩で埋める。
- `palette_pairs` は16 px幅の2列ごとに0〜3を指定し、省略時はすべて0。生成した列パレット表は `stage_header` の列パレットポインタに接続できる。現行の2軸描画は独自の行パレット処理を使う。
- `items` と `platforms` は省略できる。座標はマップ左上からのピクセル単位。アイテムは `armor`、`dagger`、`torch`、`lance`、`shield` を最大3個、足場は `obstacle`、`horizontal`、`vertical` を最大4個指定できる。移動足場の `span` は初期位置から右または上への移動距離で、固定障害物は省略または0とする。
- `enemies` は省略できる。`fixed` と `pot` は各1体で、`pot.drop` は `items` と同じ名前でドロップを指定する。敵の X は1以上、Y は足元座標とし、どちらもマップ内に収める。
- 単一グループ形式では、`enemies.scheduler` に `axis`、`page`、`zombie` と任意の `turret` を指定する。たとえば横48列のマップなら `{"axis":"horizontal","page":2,"zombie":{"x":752,"y":176},"turret":{"x":712,"y":176}}` でカメラ X が512 pxに入ったときに起動する。`axis` は記述子の縦ステージフラグに合わせる。`horizontal` の `page` はカメラ X を256 pxで割った値、`vertical` の `page` は `pan_y_page`（240 px単位）。生成時はマップ寸法で検証し、組み込み時はカメラ上限で到達できるページを指定する。ゾンビの出現は初期化後に別ページから進入した時点で始まる。開始・復帰時から対象ページにいる場合は、一度別ページに移動して戻ると始まる。

ステージバンクを `$8100` まで埋めてから生成したファイルをインクルードする。先に宣言する `stage_header` から `test_stage_width`、`test_stage_height`、`test_stage_map`、`test_stage_palettes` を参照する。`$8080` の記述子に次のフィールドを接続する。開始・復帰位置、カメラ上限、ボスは既存のヘッダと記述子に設定する。

```asm
    ; $8092..$80A9
    .word test_stage_enemy1_x, test_stage_enemy1_y
    .word test_stage_pot_x, test_stage_pot_y
    .byte test_stage_pot_drop
    .byte test_stage_item_count
    .word test_stage_items
    .byte test_stage_plat_count
    .word test_stage_plats
    .byte test_stage_sched_page
    .word test_stage_turret_x, test_stage_turret_y
    .word test_stage_zombie_x, test_stage_zombie_y
```

#### ページごとの敵出現グループ

`enemies.scheduler` の直下に `axis` と `groups` を指定すると、カメラページごとに異なる配置を定義できる。各グループに重複しない `page` と `zombie` を指定し、必要なページに `turret` を追加する。次は横32列以上のマップに指定する例。

```json
{
  "axis": "horizontal",
  "groups": [
    {"page": 0, "zombie": {"x": 240, "y": 176}},
    {"page": 1, "zombie": {"x": 500, "y": 176}, "turret": {"x": 440, "y": 176}}
  ]
}
```

組み込むときは `sd_flags` に `sd_flag_sched_table` を加え、記述子末尾の `$80BB` に `.word test_stage_sched_table` を置く。生成されたラベルはマップと同じステージバンクに置かれる。この形式では、生成された従来の出現用フィールドは無効値になる。

テーブルはページ0〜2の順に、各9 Bの `page, turret_x, turret_y, zombie_x, zombie_y` を格納する。座標は16ビットのリトルエンディアンで、未設定のページの先頭バイトは `$FF`。グループ形式では開始・復帰時のページも出現対象になり、未設定のページでは新規出現が止まる。ゾンビの出現待ちと同時出現上限はマップ全体で共有する。砲台の出現状態はページ別で、画面外回収後は再出現でき、撃破後はステージの再初期化まで撃破状態を維持する。

#### 通常ゲームモードの足場コース

`-Hardware -PlatformCourse` で、[自作マップの JSON](../tools/fixtures/platform-course.json) を変換し、通常のゲームモードの Stage 1（PRG Bank 12）に組み込む。開始・復帰・ゴールの座標は [ステージヘッダ](../src/original-course.inc) で指定する。

```powershell
./build.ps1 -Hardware -PlatformCourse
./tools/test-mesen.ps1 -PlatformCourse -UseBuiltRoms
```

1行目が出力する `build/vrc7a-test-512k-platform-course.nes` を Mesen で開き、タイトルで **START** を押す。左の床から横足場、縦足場と飛び移り、右の棚からはしごを登る。上段の右端で `COURSE CLEAR` が表示される。穴に落ちた後は **START** で再開する。

自動試験はコントローラー入力で一度落下し、チェックポイント座標、残機、両足場の初期位置を確認してから、足場の乗り継ぎ、はしご昇降、クリア表示まで進む。`-UseBuiltRoms` を省略すると、試験コマンドが ROM もビルドする。

#### 通常ゲームモードの横スクロールコース

`-Hardware -ScrollCourse` では、[横48列の自作マップ](../tools/fixtures/scroll-course.json) を同じステージバンクに組み込む。カメラのページ番号0〜2に別々の出現グループを割り当て、ページ1と2に砲台を置く。

```powershell
./build.ps1 -Hardware -ScrollCourse
./tools/test-mesen.ps1 -ScrollCourse -UseBuiltRoms
```

`build/vrc7a-test-512k-scroll-course.nes` を Mesen で開き、タイトルで **START** を押す。右へ進みながら **B** で敵を攻撃し、床の穴を **A** で飛び越える。穴に落ちた後は **START** で途中からやり直せる。右端付近のゴールで `COURSE CLEAR` が表示される。

自動試験はコントローラー入力でページ切り替えと敵の出現を確認し、穴に落ちてからワールド X=416、カメラ X=256 へ復帰する。敵の枠が初期化されて砲台とゾンビが再出現し、穴を越えて最後のグループを出現させ、クリア画面まで到達する。`-UseBuiltRoms` を省略すると ROM もビルドする。

#### 通常ゲームモードの2コース連続プレイ

```powershell
./build.ps1 -Hardware -CourseSequence
./tools/test-mesen.ps1 -CourseSequence -UseBuiltRoms
```

`build/vrc7a-test-512k-course-sequence.nes` を Mesen で開き、タイトルで **START** を押す。第1コースは移動足場とはしごを渡る構成で、上段のアイテムを取ると100点入る。`COURSE CLEAR` で **START** を押すと、スコアと残機を引き継いで第2コースへ進む。横3ページを抜け、`FINAL CLEAR` で **START** を押すとタイトルに戻る。

試験では第1コースで一度落下し、途中復帰してアイテムを取る。第2コース開始時に100点と残機2が引き継がれ、カメラ、チェックポイント、足場と敵の枠が初期化されることを確認する。最終クリア後にもう一度始めると、第1コース、0点、残機3に戻る。`-UseBuiltRoms` を省略すると ROM もビルドする。

#### Revision G の実マップ（Stage 1 の区間0）

```powershell
./build.ps1 -Hardware
./tools/test-mesen.ps1 -Stage1 -UseBuiltRoms
```

本編のビルド（`-Hardware`）は、アーケードの区間0の地形を、通常のゲームモードの Stage 1（PRG Bank 12）に組み込む。区間0は横224列（14ページ、3,584 px）。

- 地形と当たりはアーケードのとおりにした。
- 絵は今ある草・土・墓石の仮の絵で描く。
- 敵とボスは仮のもの（下の「仮の敵とボス」）。アイテムはまだ置いていない。

- タイトル → **START** → 開始の演出 → 地図 → Stage 1。演出と地図は仮の文字だけで、240フレームと150フレームで進む。**START** で飛ばせる。
- 処理は Bank 2（`$C000`、[`src/frontend.inc`](../src/frontend.inc)）に置いた。音源を呼ぶ入口（Bank 8 を `$C000` に選ぶ）は固定バンクに残る。
- 開始の演出の曲は `snd_song_title`（アーケードの開始デモの曲）。アーケードは1P START の後にコマンド `$3C`・`$3D`・`$3A` を送る。
- Stage 1 のクリア後は、自作の Stage 2 へは進まず、`STAGE1 CLEAR` から **START** でタイトルに戻る。
- タイトルの **Right+START** は演出と地図を飛ばす。`revg-stage1.lua` と `compare-player-trace.py` はこれで始める。
- 試験 `revg-boot-flow.lua` は、電源投入からタイトル、演出、地図、Stage 1 を経て、ゾンビで3回ミスし、`GAME OVER` からタイトルに戻るまでを入力だけで通す。

**仮の敵とボス**
- **ゾンビ。** 試作のゾンビ（左へ歩くだけ）を、ページ0・1・4・8・11に入ったときに出す。
  - 出る位置は、アーケードの最初のゾンビと同じカメラ X + 272（128 + 144）。
  - スケジューラの表を14ページ分にし、ゾンビの X の最上位ビットが立っていればカメラからの距離とみなすようにした。
- **一角獣の代わり。** 試作のボス（16×32、左右に往復して弾を撃つ）を門の前に置く。
  - プレイヤーが X 3392 に来ると始まる。耐久値はアーケードの一角獣と同じ10。
  - 始まるとカメラは区間0の右端（カメラ X 3328）まで進んで止まる（`sd_flag_boss_follow`）。プレイヤーは X 3336 より左へ戻れない。
  - 倒すと鍵が出て、取ると Stage 1 のクリアになる。
- **右端。** プレイヤーが右へ歩ける上限を X 3568 にした（門の前の仮のゴール X 3440 をやめた）。
- 試験 `revg-stage1.lua` は、MAME の突き合わせと同じく、ゾンビを出さない（`sched_zombies_live` を上限の2に保つ）。ボスは撃ち、低い弾は跳んでよける。

**データの流れ**
- ビルドは、[抽出ツール](../tools/mame/extract-revg-stages.py) が書いた `build/revg-stages/` を使う。無いときは先に抽出する。抽出には MAME の ROM（`reference/makaimurg.zip`、リポジトリ外）が要る。
- [変換ツール](../tools/convert-revg-section.py) が `build/revg-section0-map.inc` を書く。[`src/revg-stage1.inc`](../src/revg-stage1.inc) が、ヘッダ、記述子、湖の筏と一緒にそれを読み込む。

**変換の規則**
- **FC の行。** カメラ Y が0なので、FC のマップの行は、アーケードのマップの上から数えた行と同じになる（[FC での表示範囲](revision-g-stage-data.md#fc-での表示範囲)）。
- **足元の高さ。** 接地の値 h のタイルに立つ足元は、アーケードの Y でタイルの下端 + h + 18 になる。
  - 根拠は、開始と途中復帰の Y = 64 が、h = 14 の床の上にあること。
  - FC の足元に直すと、16 × 行 − 2 − h になる。
  - この面は、いつも1行上の FC のマスの中（上端から 14 − h px）にある。そのマスを片側床にする。h = 14 なら `mt_floor`（面がマスの上端）、h = 0〜13 なら `mt_floor_top + 13 − h`。
  - 主な床は FC の足元192、丘の上は112になる。森の低い床（行12の h = 2〜6）は184〜188、湖の手前の X 1632〜1647（h = 13）は193。
  - 森の低い床の列は、その下の地面（行13の h = 14）のマスも持つ。地面を歩いている間は低い床のマスを調べない。
- **壁と床。** 区間0には壁（左右の壁の値）が1つもない。
  - そのため、床はすべて片側床にした。
  - 丘の斜面と土の部分は背景で、プレイヤーはその前を歩く。土（`mt_dirt`）は当たりを持たない。
- **はしご。** はしごのタイルは、床と同じく1行上へずらして `mt_ladder` にする。
  - 丘の3本のはしごは、FC の行7〜11を占める。
  - 最上段は丘の上の床を兼ねる。
- **墓石・岩。** 足場の種別 `$01` の12個を、その位置の1セル（`mt_tomb`）に描く。マスには当たりがなく、当たりは表 `revg_tomb_*`（中心 X と床の高さ）をアーケードの枠（中心 X ±12、高さ ±19）で調べる。歩いては通れず、上に乗れ、前跳びでは通り抜けられる。[墓石](revision-g-player.md#墓石9e14)
- **穴と湖。** 床のない列は穴になる。
  - 湖は列103〜111。
  - 森の穴は32 px の4か所（X 1952・2016・2464・2784）。
  - 湖の筏（足場の種別 `$02`、(1664, 36)）は、横移動足場として X 1664〜1776 を往復させる。足元は218。

**まだアーケードと違う点**
- **敵とボス。** 仮のゾンビと仮のボスのまま。アーケードの敵 AI と一角獣は C-2 で入れる。
- **墓石の命中数。** 魔術師を呼ぶ命中数はまだ数えない。

**ステージの幅を広げた処理**
- 背景の描画（`two-axis-scroll.inc`）は、タイルの列番号を9ビットで持つようにした。
  - 前は1バイトだったので、8ページ（X 2048）を越えると最初の列に戻っていた。
  - 足した上位バイトは、試験が番地で読む変数をずらさないよう、`BSS` の最後に置いた。
  - 行の準備は、32列の輪を「最初の列から31まで」と「0から」の2回に分けて埋める。X を番地にそのまま使えるので、前の処理より1タイルあたり約9サイクル速い。
  - 再開時の HUD の分割について、次のことが分かった。
    - 再開時は描画を止めて画面全体を描き直し、`enable_terrain` が `$2002` を読んで次の垂直帰線を待つ。
    - 描き直しが垂直帰線の中で終わると、HUD の分割は OAM の更新の1フレーム後から始まる。それ以外の位置で終わると2フレーム後になる。どちらでも、描画を戻した最初のフレームは NMI が来ないので分割が無い。
    - これまでの `area-trial-platform-lift.lua` と `area-trial-platform-transfer.lua` は、たまたま垂直帰線の中で終わる場合（余裕は約4ライン）しか通らなかった。そのため、2フレームまで待つようにした。
    - 直した。`enable_terrain` は、HUD のある場面（2と4）では、`$2002` を読んで古い印を消してから NMI を有効にし、NMI が来るのを待ってから描画を戻す。その NMI が分割の IRQ を始めるので、描画を戻した最初のフレームから分割がある。2つの試験の待ちは無くした。描き直しが垂直帰線の中で終わったときは、前より1フレーム遅れて画面が出る。
  - ゴールとチェックポイントの列は、下位バイトを先に比べる。上位バイトから比べると1タイルあたり約35サイクル増え、最初の画面を描くのが1フレーム遅れた。512 KiB 版の `campaign-smoke.lua` は、開始から70フレーム目に時計が119になることを確かめるので、それで落ちた。
- 地形の判定（`ap_tile_type_at`）は、3ページ分の表を引くのをやめ、X ÷ 16 を計算する。
- 自弾が X 768 を越えると消える判定を外した。カメラの範囲の判定だけで足りる。

**自動試験**
- 墓石を跳び越え、最初のはしごで丘に登り、丘の上の墓石を越えて床へ降りる。
- 筏で湖を渡る。
- チェックポイントの先の穴にわざと落ち、X 1920・カメラ X 1792 から再開することを確かめる。
- 森の穴を跳び越えてゴールまで進む。
- 9ページ目では、穴の列に床のタイルが無いことを画面のネームテーブルで確かめる。8ページ目を越えた描画の確認になる。
- 32 px の穴は、右足が縁にあるうちに跳ぶ。
- 前に跳ぶには、方向を2回続けて押してからジャンプを押す。そのため筏に跳び乗るときと降りるときは、右を押し始めて2フレーム後にジャンプを押す。[歩きとジャンプ](revision-g-player.md)

**背景の絵**

アーケードの区間0の絵を、そのまま FC の背景にした。変換は [`tools/convert-revg-bg.py`](../tools/convert-revg-bg.py)、表示は [`src/revg-background.inc`](../src/revg-background.inc)。変換結果の `src/revg-section0-bg.inc` はリポジトリに入れてある（`./build.ps1 -Hardware -RefreshRevgMap` で作り直す。約1分半かかる）。

測り直した大きさは次のとおり。
- FC が表示する13行（マップの行2〜14）に、アーケードの 16 px タイルは208種類（反転とパレットの違いを別に数え、墓場・森・入れ替えの範囲ごとに分けた数）あった。
- FC は背景を反転できないので、反転を描き込んでから2ビットにすると、8×8 の絵は660種類になった。
- 背景の表の空きは219枚（$25〜$FF。$00〜$24 は HUD の文字）。墓場だけでも約310種類あり、案にあった「墓場と森の2組に分ける」方法でも入らなかった。

そこで、カメラの近くの絵だけを CHR-RAM に置き、動きに合わせて書き換える方法にした。
- **置き場所。** 8×8 の絵ごとに置き場所（スロット）を1つ決めておく。絵は、その 16 px の列がカメラの17列と左右2列ずつの範囲に入っている間だけ置く。同時に置かれることのある2枚には、別のスロットを割り当てる。
- **書き換え。** カメラが 16 px の列を1つ進むと、範囲に入った絵を待ち行列に足す。右へ進むときと左へ戻るときで別の表を持つ。NMI は1フレームに3枚（ネームテーブルの列も書くフレームは1枚）を転送する。左右2列の余裕があるので、カメラが 1.5 px/フレームで進んでも間に合った。
- **似た絵をまとめる。** どの範囲も219枚に収まるよう、いちばん混んだ範囲の中で画素の違いがいちばん少ない2枚を1枚にまとめることを繰り返す。660枚のうち46枚をまとめ、613枚になった。
- **空。** 真っ黒の絵は HUD の空白の文字 $00 を使い、スロットを取らない。
- **再開。** 描画を止めている間に、カメラの列0からいまの列までの表を順に転送する。各スロットには最後に入った絵が残り、それがいまの範囲の絵になる。

ネームテーブルは縦ミラー（64列の輪）にした。
- 16 px ごとにパレットが変わるので、属性の1バイト（32 px 四方）を列ごとに書き換える。横ミラー（32列の輪）では、そのバイトのもう半分が画面の左端に見えていて色が変わってしまう。64列の輪なら、もう半分は画面の外にある。
- HUD はネームテーブル0の上4行で、HUD の後のラスター分割はカメラ X の8ビット目で左右のネームテーブルを選ぶ。

パレットの決め方は次のとおり。
- アーケードの色を、2C02 の色から最も近いもの（Lab の距離）に置き換える。各 16 px タイルは、自分を最もよく描けるパレットを1つ選ぶ。
- 費用は、描いた画素の色の誤差の合計に、タイルの中の違う2色が同じ色になったときの損失（2色の距離×少ない方の画素数×2）を足したもの。損失の項が無いと、木の幹と山の近い色がすべて1色になった。
- パレットは6組を探す。0と1は全体で共有し、2と3は墓場用、4と5は森用（入れ替え後に2と3へ入れる）。40通りの初期値から、色を1つずつ替える局所探索で決める。
- 入れ替えはカメラの列97（湖の手前）で行う。その前後で見えている列（96〜113）は、共有の0と1だけを使う。
- 固定した色。P0 の色1は HUD の文字の灰色 $10、色2は $00（山・墓石・門の石が全体で2段の灰色を持つ）。地面（アーケードのパレット6）は、どこでも P1 を使う。入れ替えの前後で地面の色が変わらないようにするため。水のタイルは重みを8倍にした。水は少ないので、重みが無いと青が残らなかった。
- 決まったパレットは次のとおり。共有 $10/$00/$02（灰色と水）、$0A/$17/$19（地面）。墓場 $08/$17/$19、$0A/$19/$28。森 $0A/$19/$28、$00/$19/$10。

NMI の時間は、ステージを 1.5 px/フレームで通した間、最も遅いフレームでも垂直帰線の開始から17.6ライン（20ラインのうち）で終わった。

**背景の絵のまだ違う点**
- 森の木の幹と枯れ木は、茶色1色になり、木目が出ない。幹の茶色の濃淡（$07・$17・$27）を入れると、門の灰色か葉の緑が足りなくなる。
- 丘の上の墓石は緑がかった灰色になる。
- アーケードの属性 bit 3（スプライトより手前に描くタイル、区間0では4種類・203か所）はまだ扱っていない。
- 46枚の絵を、似た別の絵で代用している。

### 3.4 PNG の NES パレットを生成する

自作の背景やスプライトには、Python と Pillow で動く `tools/fit-nes-palettes.py` を使う。使用する色見本は RGB 3バイト × 64色（色番号順、計192バイト）のバイナリを渡す。

```powershell
python tools/fit-nes-palettes.py bg.png build/bg-indexed.png build/bg-palette.json --mode bg --rgb-table nes.pal --backdrop 0x0f
python tools/fit-nes-palettes.py obj.png build/obj-indexed.png build/obj-palette.json --mode obj --rgb-table nes.pal
```

- BG は不透明な16×16 px区画ごとに1組を使う。各組のスロット0は `--backdrop` で共通に指定し、追加の3色を推定する。
- OBJ は文字やキャラクターのシートを8×16 px単位で区切る。アルファ0をスロット0に割り当て、アルファ255の画素をスロット1〜3に減色する。半透明は入力エラーになる。
- 各区画の色候補から、画素数で重み付けした RGB の誤差が小さくなるよう4組まで選ぶ。ディザリングは行わない。入力と色見本が同じなら結果も同じになる。
- JSON の `palettes` は NES の色番号を4組×4色、`palette_ids` は左上から行順で区画ごとの番号（0〜3）を格納する。PNG の画素インデックスの下位2ビットが CHR 用の色番号になる。OBJ の透明画素は全組で PNG インデックス0を使う。

BG と OBJ は別々に実行する。現行のマップコンバータが受け取る `palette_pairs` は列単位のため、BG の `palette_ids` をそのまま渡すことはできない。

### 3.5 CHR パターン表を生成する

変換済みの PNG とパレット JSON を `tools/pack-nes-chr.py` に渡す。1枚の画像を1つのパターン表向けにパックし、ca65 のインクルードを出力する。

```powershell
python tools/pack-nes-chr.py build/bg-indexed.png build/bg-palette.json build/bg-chr.inc --prefix area_bg --first-tile 0x40
python tools/pack-nes-chr.py build/obj-indexed.png build/obj-palette.json build/obj-chr.inc --prefix area_obj
```

| シンボルの接尾辞 | 内容 |
| --- | --- |
| `_chr_vram`、`_chr_size`、`_chr` | 転送先の PPU アドレス、転送バイト数、2bpp パターン列 |
| `_palette` | 4組×4色のパレット。PPU に書くときは OBJ の各組のスロット0を飛ばすか、OBJ の後に BG を書く |
| `_region_columns`、`_region_rows` | 区画表の列数と行数 |
| `_regions` | 左上から行順。BG は左上・右上・左下・右下のタイル番号とパレット番号の5バイト。OBJ は奇数の OAM タイル番号と属性下位2ビットのパレット番号の2バイト。全透明 OBJ 区画は `$00,$FF` で、OAM へ転送しない |

BG は `$0000`、8×16 OBJ は `$1000` のパターン表を使う。`--first-tile` は表内の最初の空き番号（OBJ は偶数、既定値は0）で、既存の文字やスプライトのタイルを前方に予約できる。BG は同じ8×8タイル、OBJ は同じ8×16ペアを共用する。パレット番号は区画別に保持される。出力が予約領域を含めて各表の4 KiBを越える場合は変換エラーとなる。

### 3.6 OBJ メタスプライトを生成する

OBJ の変換に `--poses` を付けると、複数の8×16スプライトからなるポーズも同じインクルードに出力できる。JSON のキーがポーズ名で、`region` は OBJ シート左上を `[0, 0]` とした区画の `[列, 行]`。`dx` と `dy` はポーズの基準点からスプライト左上への符号付きピクセル差分（−128〜127）。`flip_x` と `flip_y` は省略時 `false` で、各8×16スプライト内を反転する。

```json
{
  "idle": [
    {"region": [0, 0], "dx": -8, "dy": -16},
    {"region": [1, 0], "dx": 0, "dy": -16, "flip_x": true}
  ]
}
```

```powershell
python tools/pack-nes-chr.py build/obj-indexed.png build/obj-palette.json build/obj-chr.inc --prefix area_obj --poses build/obj-poses.json
```

- `area_obj_pose_count` はポーズ数。`area_obj_poses` は JSON のキー順に並ぶ16ビットアドレス表。
- `area_obj_pose_idle` の先頭1バイトは有効なスプライト数。以降は `dx, dy, OAM タイル番号, OAM 属性` の4バイトずつ。差分は2の補数で、属性はパレット番号と反転ビットを含む。描画側で差分を画面上の基準点に加え、クリッピングとスプライト左上 Y から OAM Y への変換（1減算）を行う。
- 配列の先頭から OAM に置くと、ポーズ内の重なりでは先に書いたパーツが優先される。全透明区画は OAM 枠を使わず、出力から省かれる。同一ポーズで相対走査線に9枚以上重なる場合と、1ポーズが64枚を超える場合は変換エラーになる。別のキャラクターなどと重なった場合の優先度はゲーム側の OAM 割り当てで管理する。

### 3.7 エリアの画像データを PRG-ROM に配置する

`pack-nes-chr.py` で BG を `--prefix bg`、OBJ を `--prefix obj --poses <ポーズJSON>` で生成する。エリアマニフェストは、エリア名から両方のインクルードファイルへの対応を指定する。相対パスの基準はマニフェストのあるディレクトリ。

```json
{
  "area_a": {"bg": "area-a-bg.inc", "obj": "area-a-obj.inc"},
  "area_b": {"bg": "area-b-bg.inc", "obj": "area-b-obj.inc"}
}
```

```powershell
./build.ps1 -Hardware -AreaManifest build/areas.json
```

追加データを含むROMは `build/vrc7a-test-512k-areas.nes`。マニフェストの順に、エリアごとに BG・OBJ の順でそれぞれ8 KiBのバンクを割り当てる。候補は `BANK19`〜`BANK50` で最大16エリア。各バンクの先頭1バイトは既存の識別タグ用で、残りに CHR、パレット、区画表、OBJ のポーズ表を収める。超過時はリンカーが対象バンクを報告する。

`nes_area_directory_bank`（`BANK11`）を `$8000` に切り替えると、`nes_area_count` でエリア数、`nes_area_table` で同じ順序の参照表を読める。1エリアに BG・OBJ の18バイトのレコードが1件ずつ並ぶ。描画側では使用するレコードを RAM に退避してから画像データのバンクへ切り替える。

| オフセット | 内容 |
| --- | --- |
| 0 | `$8000` に切り替える PRG バンク番号 |
| 1、3 | CHR 転送先の PPU アドレス、転送バイト数 |
| 5、7 | CHR データ、パレットデータの CPU アドレス |
| 9、11 | 区画表の列数、行数 |
| 13、15 | 区画表、ポーズアドレス表の CPU アドレス。BG のポーズ表は0 |
| 17 | ポーズ数。BG は0 |

オフセット1〜16の各値は16ビットのリトルエンディアン。

追加ビルドでは、テストメニューの **左＋A** でエリアビューアに入る。ビューアのコードは `BANK51` を `$A000` に割り当て、参照表と画像データは `$8000` で読み分ける。画面を一時的に消して CHR とパレットを転送し、BG シート左上の16列×15行までを描画する。小さいシートは繰り返して画面を埋める。OBJ は画面内の座標 (128, 128) を基準に描画し、ポーズ切り替え時は VBlank 中に OAM を更新する。[操作方法](../README.md#マニフェストのエリアビューア)

### 3.8 エリア BG を試験コースに組み込む

`-Hardware -AreaManifest build/areas.json -AreaTrial build/trial-stage.json` でコースを追加する。複数コースは `-AreaTrial @('build/first.json', 'build/second.json', 'build/third.json')` のように最大11個まで指定できる。テストメニューから **左＋B** で1番目、**右＋B** で2番目を始める。3コース以上の構成では **上＋B** で選択画面を開き、任意のコースを開始できる。クリア画面の **START** で引数順に進み、最終コースのクリア後は **START** で再プレイできる。試験コース JSON の項目は次のとおり。

| 項目 | 内容 |
| --- | --- |
| `area` | エリアマニフェストに登録した名前 |
| `tiles` | `convert-stage-map.py` と同じ行優先の配列。48列×15行。各列の最初の `ledge` または `rock` が Y=48～224 の床になる。両方ともない列は落とし穴になる |
| `regions` | `sky`、`gravel`、`ledge`、`rock`、`oneway`、`ladder`、`hazard` を BG シート内の `[列, 行]` に対応付けるオブジェクト。座標は左上を `[0, 0]` とする |
| `start_x`、`checkpoint_x`、`goal_x` | ワールド X 座標をピクセル単位で指定。開始は16～239、復帰は開始の16 px 以上先かつ736以下、ゴールは復帰の16 px 以上先かつ760以下 |
| `checkpoint_y`、`goal_y` | 任意。指定した X の列にある `oneway` の上端、または通常床の Y 座標をピクセル単位で指定する。16 px 刻みで最小値は16。省略時は通常床を使う |
| `player_poses` | 任意。立ち、歩き、ジャンプに使う OBJ ポーズ名。省略時は試験コース標準のプレイヤー画像を使う |
| `enemies` | 任意。固定敵 `fixed` と射撃敵 `ranged` の配置 |
| `moving_platform` | 任意。横または縦に移動する足場1台の座標 |
| `moving_platforms` | 任意。移動足場1～2台の配列。`moving_platform` との併記は不可 |

BG を `pack-nes-chr.py --first-tile 0x40` でパックすると、HUD と目印に使う既存パターンを保てる。参照する7区画には同じパレットと背景色 `$0F` を使う。ビルドで CHR の重複、区画座標、リンク後のパレット番号と背景色を検査する。ゲーム内ではそのパレットの色1～3を BG パレット1に割り当て、HUD はパレット0を使う。

`BANK52`〜`BANK62` に引数順で地形と区画表へのオフセットを配置する。コース開始・再挑戦時は `BANK51` の転送処理がエリア参照表を読み、描画を止めている間に BG を CHR-RAM へ転送する。スクロール中は RAM に展開した7種類のタイル番号を参照する。メタタイルの描画と床判定は同じ JSON を使う。通常床と開始位置の足元は各列の最初の `ledge` または `rock` で決まる。[Mesen での操作](../README.md#マニフェストの試験コース)

`checkpoint_y` を指定すると、指定の X と足元の Y が一致して接地したときにチェックポイントが有効になり、再挑戦もその座標から始まる。省略時は `checkpoint_x` 以上に達すると有効になる。ゴールは X と足元の Y が一致して接地すると成立する。

落とし穴で足元がマップ下端の Y=240 に達すると被弾扱いになり、START で再挑戦できる。開始地点と明示的に配置する敵には通常床が必要。穴の上にチェックポイントやゴールを置く場合は、支えになる `oneway` の高さを指定する。

移動後にプレイヤーの中心 X と足元の1ピクセル上を調べ、その位置が `hazard` のセルなら被弾する。床の直上に `hazard` を置くと、歩いて踏み込んだときに被弾し、ジャンプでセルより高く越えると回避できる。被弾後は START で再挑戦し、通過済みのチェックポイントがあればそこから再開する。

`oneway` は片側足場として使う。プレイヤーの中心 X が足場の列にあり、下降中の足元がそのセルの上端に達すると着地する。下から上昇するときは通り抜けられ、立った状態で端を越えると落下する。

`ladder` は同じ列のセルを縦に並べて配置する。プレイヤーの中心 X をその列に合わせ、下端で上、上端で下を押すと毎フレーム1ピクセルずつ昇降する。上下入力を離すとその場で止まる。はしご列の最上端は片側足場と同じ高さの判定を持つため、隣の列に同じ高さの `oneway` を置けば乗り移れる。

#### 試験コースの横移動足場

```json
"moving_platform": {"left_x": 119, "right_x": 176, "y": 160}
```

中心 X が `left_x` と `right_x` の間を往復する。X は `start_x + 8 ≤ left_x < right_x ≤ goal_x - 8`、上端 Y は40～224。開始・再挑戦時は左端から動き出す。

#### 試験コースの縦移動足場

```json
"moving_platform": {"x": 96, "top_y": 104, "bottom_y": 160}
```

中心 X は固定で、上端 Y が `top_y` と `bottom_y` の間を往復する。X は `start_x + 8 ≤ x ≤ goal_x - 8`、Y は `40 ≤ top_y < bottom_y ≤ 224`。開始・再挑戦時は下端から上へ動き出す。

#### 試験コースで足場を組み合わせる

```json
"moving_platforms": [
  {"left_x": 71, "right_x": 127, "y": 160},
  {"x": 144, "top_y": 104, "bottom_y": 176}
]
```

各足場は指定した経路を往復し、コース開始・再挑戦時にそれぞれの初期位置に戻る。2台の上端が重なり、プレイヤーが両方の範囲内に立っている場合は、配列の先頭側の足場がプレイヤーを運ぶ。

横・縦とも幅は16 pxで、2フレームに1 pxずつ移動する。経路全体で足場が覆う列の通常床は、足場と同じ高さかそれより下に配置する。通常床のない列にも置ける。プレイヤーは下から通り抜けられ、下降中に足場の上端へ着地する。上に立っている間は足場と一緒に移動する。足場の画像は組み込みの CHR を使う。

#### 試験コースのプレイヤーポーズ

`player_poses` の4項目を、エリアの OBJ 用 `--poses` JSON の名前に対応付ける。

```json
"player_poses": {
  "idle": "rest",
  "walk_a": "stride",
  "walk_b": "step",
  "jump": "air"
}
```

OBJ シートは `pack-nes-chr.py --first-tile 0x10 --prefix obj --poses poses.json` でパックする。選択した各ポーズには1～2個の不透明な 8×16 パーツを指定し、4ポーズで同じ OBJ パレットを使う。座標の原点は足元の中央で、右向きの左上オフセットを `dx=-16..8`、`dy=-32..-1` で指定する。歩行は地上で8 px 進むごとにコマを切り替え、左向きはパーツ座標と横反転ビットを反転する。

開始・再挑戦時に OBJ の CHR を `$1100` 以降へ転送し、選んだパレットを OBJ パレット0に割り当てる。移動足場とプレイヤーポーズを併用する場合は、足場が使う `$1100–$113F` を避けるため `--first-tile 0x14` 以上の偶数を指定する。被弾中は立ちポーズに被弾色を適用する。プレイヤーは OAM の先頭2枠を使う。試験コースの敵と弾は既存の CHR・パレット・OAM 枠を使う。

#### 試験コースの敵配置

```json
"enemies": {
  "fixed": {"x": 258, "y": 176},
  "ranged": {"x": 524, "y": 176}
}
```

両方とも `x` は敵の中心、`y` は足元のワールド座標をピクセル単位で指定する。`x` の範囲は固定敵が8〜760、射撃敵が12〜760。`y` はその列の最上段の床と一致させる。

`enemies` 全体を省略すると従来の配置を使う。`enemies` を指定した場合は、記載した敵だけが出現する。空オブジェクト `{}` で敵を出さないコースにできる。射撃敵は左側のプレイヤーを狙い、弾はページ境界を越えて進み、床かコースの左端に達すると消える。再挑戦時はチェックポイントの有無にかかわらず、指定した敵を初期位置に戻し、敵弾と射撃の待ち時間をリセットする。
